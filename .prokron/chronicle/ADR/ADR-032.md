# ADR-032: Releases are archived and citable
- Date: 2026-09-22
- Status: ACCEPTED
- Authority: product owner
- Supersedes: none
- Amends: none
- Corrects: none
- Rejects: letting the archive infer its own metadata from the repository; naming a person as author without confirming how they wish to be credited
- Affects: T-DOI-01
- Context: A release on a code host can disappear with the account that owns it, and a repository URL is not something a paper can cite. Zenodo archiving was enabled for the repository, which mints a persistent identifier for each release from that point on. Left alone it would derive the title, authorship and description from whatever the repository happened to say that day, and a deposited record is a durable thing to get wrong.
- Decision: The repository carries its own archive metadata — `.zenodo.json` for the deposit and `CITATION.cff` for readers and for the citation affordance on the code host — so the record says what the project actually is rather than what could be inferred from it. Authorship is recorded as the organisation, `Qomero`, because a personal name and an ORCID are the author's to give and were not confirmed; a deposited record can be edited afterwards, and this is the part most worth revisiting deliberately. The version and release date in `CITATION.cff` are part of what a release changes.
- Consequences: Every release from now on is preserved independently of the code host and has an identifier that outlives it, and the concept identifier resolves to the latest version, so a citation does not go stale. Releases made before archiving was enabled are not retroactively deposited, which is worth knowing when reading the version history. The metadata is now a second place the version appears, so a release that updates one and not the other is inconsistent — the documentation tests already hold the README to `VERSION`, and this is the same class of drift.
