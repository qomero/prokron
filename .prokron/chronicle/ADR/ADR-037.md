# ADR-037: Offer an opt-in, evidence-cited baseline of existing decisions
- Date: 2026-09-23
- Status: ACCEPTED
- Authority: product owner
- Supersedes: none
- Amends: ADR-008
- Corrects: none
- Rejects: reconstructing tasks, journal entries, or intent for pre-Prokron history; scanning a repository during `existing` initialization; importing or synchronizing external trackers; copying existing ADR files into the chronicle
- Affects: T-BASELINE-01
- Context: An `existing` installation starts empty by design (ADR-008, SPEC §3.2). That keeps the chronicle honest, but decisions the code already depends on — datastore, authentication, API style, deployment target — have no ADR. An agent can contradict one, and the arbitration order cannot help because nothing is recorded to rank. SPEC §3.2 already permits reconstruction on explicit request but gives it no shape, so any attempt today is unbounded and indistinguishable from a decision recorded at the time it was made.
- Decision: Add a separate portable workflow, `/prokron-baseline`, run only when the owner explicitly asks and never by `init`. It proposes ADRs for load-bearing decisions only, at most ten per run, and creates no tasks, journal history, or intent. Each baseline ADR carries `Origin: RECONSTRUCTED` and an `Evidence:` field naming the repository paths or documents the decision was inferred from; an existing ADR directory is cited there, not copied. Baseline ADRs are written `PROPOSED` and become `ACCEPTED` only when the owner confirms them and is named in `Authority:`. Validation reports an error for a reconstructed ADR with no evidence, and for an accepted one whose authority names no human. Compiled views and the dashboard label reconstructed decisions distinctly from contemporaneous ones. `existing` initialization remains empty by default.
- Consequences: A brownfield project can capture the constraints it already lives under without the chronicle claiming history it never observed. The cap keeps the step reviewable in one sitting and limits it to decisions that bound future work. Rejected or unconfirmed proposals stay visible as `PROPOSED` rather than silently gaining authority. Implementation waits for the ADR-035 hierarchy to land, because it touches the same parser, validator, and views.
