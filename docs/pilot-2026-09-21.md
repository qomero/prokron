# Continuity pilot — observed results

- Host: Codex CLI 0.155.0 (codex exec, non-interactive)
- Prokron: 0.2.1, installed by install.sh from the source checkout
- Date: 2026-09-21
- Project: disposable "Tea Timer" repository, /tmp/pilot

## Step 1 — install and initialize
### new mode
First attempt ran under Codex's default read-only sandbox. Worth recording
rather than discarding: the agent read AGENTS.md and commands/prokron-init.md,
recognised that the chronicle was empty so `new` mode applied, drafted the task
set from SPEC.md, and then stated plainly that initialization was blocked, that
no files had been changed, and what the next action was. It did not pretend to
have written anything. It also discovered and ran `./bin/prokron validate` on
its own initiative, without being told the tool existed.

Second attempt, with `--sandbox workspace-write`: PASS.

From SPEC.md alone the agent derived six product tasks — tea selector, timer
controls, chime, remembering the last tea, offline loading, and a verification
task that owns the phase exit. That is the five stated requirements plus a
closing task, with nothing invented beyond them. It wrote 20 acceptance criteria
across them, four ADRs recording the choices the spec left open (tea presets,
offline strategy), one phase with a gate, and a real dependency chain: T-001
ready, T-002 through T-006 blocked behind it.

It also claimed a task for the initialization itself (T-000, WIP) before doing
the work, which is the "record the task before implementation" rule firing with
no Prokron command given. Unprompted, it discovered `./bin/prokron`, and its own
`validate` and `compile` runs pass.

### existing mode
PASS. Installation produced an empty chronicle: TASKS.md "No tasks yet.",
JOURNAL.md "No sessions recorded.", prokron/ADR/ holding only its index. The
pre-existing lib.py was untouched. No history was invented.
The runtime installed alongside: ./bin/prokron reports 0.2.1 and validates the
empty chronicle without error.

## Step 2 — work request with no Prokron command
PASS.

The request was "Add a dark mode toggle to the tea timer, remembered between
visits. Implement it." No Prokron command, and deliberately work that was not in
the derived task list, so claiming an existing task was not an option.

The agent created T-007 "Remembered dark mode toggle" with its own acceptance
contract (5 criteria), implemented it in index.html, and closed the task. It
first claimed T-001, the task the page itself belonged to, because the toggle
needed a page to live on — a reasonable reading of the dependency rather than a
deviation.

At the end INTENT.md is cleared and carries the next action with the exact
command to run. `prokron validate` passes. The graph stayed in sync throughout;
`prokron status` recomputes it from authority, so it cannot drift.
