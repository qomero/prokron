# Continuity pilot — observed results, v0.4.0

Supersedes the partial run in `pilot-2026-09-21.md`, which was measured against
v0.2.1 and cites `./bin/prokron` and a `prokron/` directory that no longer
exist.

- Prokron: 0.4.0, installed by `install.sh` from the source checkout
- Hosts: Codex CLI 0.155.1 via `codex exec --sandbox workspace-write`;
  Gemini 3.8 Flash for step 5; the product owner for step 7
- Date: 2026-09-22
- Projects: a disposable Tea Timer repository from a five-requirement
  specification, and a two-file Python library for `existing` mode

## Step 1 — install and initialize · PASS

Installing takes one line with no arguments. Both targets received one
directory, `.prokron/`, plus the host-addressed files; nothing else was written
to either repository root.

`existing` mode invented nothing: `TASKS.md` read "No tasks yet.", status
reported an empty project, and the two pre-existing source files were untouched.

`new` mode: from five stated requirements the agent derived three product tasks
plus a verification task owning the phase exit, 11 criteria, one phase with an
exit authority and a gate, and ADR-001 for the grouping choice the
specification left open. Dependencies were real — `T-001` ready, `T-002` and
`T-003` blocked behind it. It claimed `T-INIT` as `WIP` for the initialization
itself before doing the work, with no Prokron command telling it to.

Two failures were the harness, not the product, and are recorded so the next
run avoids them: Codex refuses to operate outside a git repository, and
overriding `HOME` to sandbox the launcher also hid Codex's own credentials.

## Step 2 — work without a Prokron command · PASS

Request: "Add a subtract function to calc.py, with a test for it." No Prokron
command, no mention of tasks.

The agent created `T-001`, wrote contract `AC-T-001` and recorded it as "Frozen
on 2026-09-22 when T-001 became WIP", implemented, recorded evidence naming the
command it ran and the assertions it covered, set validation `SYNTHETIC` rather
than claiming more, cleared intent, and appended a journal entry.

Unprompted, it discovered the tool and ran `prokron validate` four times,
`status` twice and `compile` once — using the bare command, which also exercises
the v0.4.0 launcher from an agent rather than a person.

## Step 3 — a decision, then its reversal · PASS

"Remember the last tea using localStorage." produced ADR-003. "Change that:
store the last tea in a cookie instead, because the server needs to read it."
produced ADR-004, `Supersedes: ADR-003`.

ADR-003 survives unedited, still `ACCEPTED`, and the index carries the chain in
both directions. Neither session was given `/prokron-decide`.

## Step 4 — stopping partway · PASS

"Start the countdown work, but stop as soon as the tick logic runs. I have to
leave, so do not finish the task."

`INTENT.md` recorded the stopping point precisely enough to resume from: start
displayed 3:00, the interval callback displayed 2:59 after one simulated
second, no further implementation or timer verification performed. It named the
next action and the command to begin it.

The journal recorded what was left mid-air — pause/resume, chime, complete
tests, browser evidence — and the task stayed `WIP` with every criterion
`NOT_RUN`. Validation was recorded as synthetic with browser and server
integration called out as unverified.

No host limit warning was available to observe. Nothing was simulated, so
nothing is claimed about quota detection.

## Step 5 — a cold agent resumes · PASS

A Gemini 3.8 Flash session with no prior chat, given this repository and asked
only "tell me about this project, I'm new Project manager", answered in about
thirty seconds.

It reported all four progress figures exactly as compiled, named the phase held
at a gate and the task responsible, stated the authored-versus-compiled
boundary, the contract freeze, the completion rule and all seven levels of the
arbitration order in the right order, and gave the same two next actions as
`HANDOFF.md` — before reading implementation code.

Two imprecisions: it listed an unopened phase under a phase breakdown, marked
"Up Next" rather than given a status, and cited the internal specification
directory, which is accurate locally and a dead reference publicly.

It also exposed a defect. `HANDOFF.md` still directed the next agent to a path
that moved when phase specifications became internal. The agent silently used
the current location and was therefore more correct than the handoff it was
reading. A prose path is not a reference the compiler resolves, so neither
validation nor any test could have caught it. The handoff was corrected.

## Step 6 — initializing again over populated history · PASS

The installer, re-run over a populated project, left the chronicle byte for byte
identical and printed the resume instruction rather than the init one.

The agent, given `$prokron init new` a second time, changed exactly two files:
`JOURNAL.md`, appended to with zero lines removed, and `HANDOFF.md`, which is
overwritten by design. `TASKS.md`, `ACCEPTANCE.md`, `PHASES.md`, `INTENT.md`,
the chronicle guide and every ADR were byte-identical. Six tasks, five ADRs and
five journal entries survived intact.

Its own summary: "`new` is an entry mode, not a reset of populated history", and
on the outstanding validator warning, "No evidence was removed to silence the
warning."

## Step 7 — a person reads the chronicle · PASS

Recorded by the product owner, who commissioned the work but did not write the
chronicle. They opened the generated dashboard for this repository and for a
second, unrelated project, and report that the record is understandable to a
person and clear as project management.

They did not record a point-by-point account, and no comparison against an
agent's account of the same chronicle was made. The criterion passes on the
owner's authority with that limit stated.

## Observations worth keeping

- The one validator warning raised across the whole pilot was
  `premature-evidence` on a `WIP` task carrying partial evidence. That is the
  validator working as designed, and recording partial evidence mid-task is
  also reasonable. Whether the warning should fire at all on a `WIP` task is
  worth revisiting; it was not silenced.
- Two of the three agents used the chronicle without being told it existed.
- Nothing in this pilot measured behaviour against a real host limit. Prokron
  cannot read a quota counter a host does not expose, and that claim remains
  untested rather than passed.
